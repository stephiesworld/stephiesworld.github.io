The 60-second pitch

Start here — this is what you say first

You point it at a codebase that uses the Claude API. It tells you what will break, what is silently costing money, and what is untested.

The reason it exists: that is the job an AI deployment manager does by hand every week. You read a customer's integration and tell them what's wrong with it. This automates the boring, mechanical two-thirds of that.

The interesting part isn't the checks — it's the split. Roughly thirty checks run with no model at all: they read the code directly, cost nothing, and give the same answer every time. Exactly one step uses a model, for the questions no rule can answer.

Say that split out loud in the interview. It's the design decision, and it's the thing most people get wrong in the other direction — reaching for a model to do something a twenty-line function does better.

If they ask "why not just use an LLM for all of it?"

Because "is this model ID retired?" is a lookup, not a judgement call. A table answers it correctly every time, for free, in a millisecond. A model answers it correctly most of the time, for money, and occasionally invents a retirement date that sounds right. You use the model where there's genuinely no rule to write.

The one big idea

Workflow vs. agent — the thing they're actually testing

In plain words

There are two ways to build something with an AI model, and picking the right one is most of systems design.

A workflow is when you decide the steps ahead of time. Step one, then step two, then step three. You wrote the order.

An agent is when the model decides the next step while it's working. You give it tools and a goal; it chooses what to do next based on what it just found.

The test for which one you need is a single question:

Can you write down the list of steps before you start?

If yes, build a workflow. It's cheaper, faster, and you can actually test it. If no — if which step comes next depends on what you discover — you need a loop.

WorkflowAgent
Who picks the next stepYou, at design timeThe model, at run time
Shape of the workKnown in advanceDiscovered while working
TestingEasy — test each stepHard — test outcomes, not steps
Cost & speedPredictableVariable, usually worse
How it failsWrong order, silentlyWanders, loops, over-explores

This project is deliberately both, which is why it works as an interview example — you can point at the same codebase and show the decision going each way:

the checks → workflow. Parse, compare to a table. Steps are known. --llm → still a workflow. One call. We already know which files matter, so we can assemble the whole question up front. No loop needed. --llm-agent → a real agent. The reviewer gets search and read tools and decides what to open next. You cannot assemble that question in advance, because which file matters depends on what it just read.
If they ask you to design an agentic system

Don't start with "I'd use an agent." Start with: "First I'd check whether this is actually agentic — can I name the steps up front? If I can, a workflow is cheaper and testable. If I can't, here's where the loop goes." That answer alone puts you ahead of most candidates.

The vocabulary

model.py — the words every other part speaks

In plain words

Before anything else, the project defines its nouns. There are only four that matter: a Location (a file and a line number), an Arg (one setting in an API call), a CallSite (one place the code calls Claude), and a Finding (one problem we found).

This sounds like bookkeeping. It's the thing that makes the project extendable. Because the checks only ever look at these four shapes, they never touch raw code — which means adding support for a new programming language is one new file, not edits to thirty check functions.

The severity levels are worth memorising, because the definitions do real work:

  • Critical The API rejects this. It fails today, every time.
  • High Silently wrong, silently expensive, or silently truncated.
  • Medium Real money or quality left on the table.
  • Low Cleanup. Dead settings, stale flags.

The High band is the one to talk about. Everything in it shares one property: no error is raised. That's precisely why a human reviewer misses it and a tool shouldn't. If someone asks what the tool is for, that's the answer — not the loud failures, the quiet ones.

One detail worth understanding, because it comes up again and again: resolved. It separates "we know this is wrong" from "we couldn't see it." Checks are required to stay silent about the second. A tool that guesses is worse than a tool that says nothing.

The facts that rot

knowledge.py — everything with an expiry date, in one file

In plain words

The tool needs to know things that change: which models exist, what they cost, when old ones get switched off, which settings now cause an error. All of that is guaranteed to go out of date on someone else's release schedule, not yours.

So it all lives in one file, with a date stamped at the top that gets printed in every report. Updating the tool is a change to that one file. If those facts were sprinkled across the thirty check functions, the tool would be wrong within a few months and nobody would know which lines to fix.

There's a second trick here that's worth stealing, and it's the part interviewers like. The checks never ask "which model is this?" They ask "does this model reject that setting?"

Because behaviour is stored as data rather than written into logic, a new model release is one new row in a table. Nothing else changes. If instead the checks said "if the version is 4.7 or newer…", every release would mean hunting through the code for version comparisons.

The date is passed in, never looked up

Notice status_on(on: date) takes today's date as an argument instead of asking the computer for it. That's deliberate. It means a test can ask "what's the status on July 1st?" and "what about September 1st?" and get different, correct answers — without any clock-freezing trickery.

If they ask about testing time-dependent code

Don't reach for a mocking library. Pass the time in as a value. It's simpler, it's honest, and the test reads like the thing it's testing.

The fact that justifies the whole tool

Caching lets you avoid re-paying for the unchanged part of a prompt. But every model has a minimum size below which it silently won't cache — no error, the setting is just ignored.

ModelMinimum
Claude Opus 5512 tokens
Claude Opus 4.81,024 tokens
Claude Opus 4.72,048 tokens
Claude Opus 4.64,096 tokens

Those numbers don't go in one direction. A 750-token prompt caches on Opus 5 and silently stops caching on Opus 4.6. So a team can "upgrade" and start paying ten times more for the same thing, with nothing in the code looking different and no error anywhere.

That's the single best example to give if someone asks why a tool like this is worth building. No human catches that in code review.

Reading the code

extract/ — turning source text into facts

In plain words

To check someone's code you first have to understand it. Not run it — just read its structure. Python has a built-in tool for this that turns source text into a tree: which lines are function calls, what arguments they were given, and so on. That tree is called an AST, short for abstract syntax tree.

This part walks that tree looking for calls to the Claude API, and records what settings each call was given. It's the translation layer between "text in a file" and the tidy shapes from the last section.

The bug that taught me the most

My first version used Python's built-in "read this literal value" function. It's all-or-nothing: if any single piece of an expression is a variable rather than a fixed value, it gives up on the entire thing.

The rule about guessing

If the same name is given two different values, the extractor resolves it to neither:

Guessing would produce a confident, detailed, completely wrong finding about code that doesn't exist. That's the worst thing this tool can do — worse than missing a real problem, because it destroys trust in everything else in the report.

The checks

checks/ — thirty small functions, no model involved

In plain words

Each check is one small function. It gets handed the facts the extractor found, and it hands back a list of problems. That's the whole shape.

They're registered with a decorator — a line above the function that says "add me to the list." That means adding a new check is writing one function. There's no central list to update, so two people can add checks without stepping on each other.

The house rule

There's one rule the whole folder follows, and it's worth quoting verbatim:

Prove it from the facts, or stay silent.

Anything needing taste — is this prompt any good? will this tool description actually work? — is not allowed here. It goes to the model instead. A rule-based check that guesses produces confident nonsense, and confident nonsense is worse than no finding at all.

The false-positive problem, and a real fix

When I ran the tool on itself, it reported 19 problems in its own model catalog — the file that has to list retired models in order to know they're retired.

That's the general version of a real issue: some files use a model, others describe one. A price list or a routing table legitimately keeps old entries. Reporting each as a defect buries the real findings.

The fix: if one file mentions six or more different models, treat it as a catalog and collapse it to a single summary line. Self-audit noise dropped from 51 findings to 29.

If they ask about false positives

Say this: a linter that can't be satisfied gets turned off, and then it catches nothing. Suppressing noise isn't cheating — it's what makes the real findings visible. And there's a test fixture that's deliberately clean, asserting the tool stays quiet on good code.

The judgement pass

llm.py — one call, for what no rule can decide

In plain words

Some questions have no rule. Is this prompt contradicting itself? Will the model actually reach for this tool, or is the description too vague? Is this whole architecture the wrong shape for the job?

For those, the tool makes one call to Claude with the relevant files. Not a loop — we already know which files matter, so the entire question can be assembled up front and asked once.

The most important line in the prompt is a "don't"

Without that, you get a worse-worded duplicate of the checks. The prompt also explicitly says an empty answer is fine — because a model asked to review something will always find something unless you give it permission not to.

It eats its own cooking

The request this file makes deliberately does all the things the checks look for in other people's code: a current model, caching switched on correctly, a structured response format, and a check for refusals before reading the answer.

There's a comment in the file explaining why the instructions are stored as a fixed value rather than built fresh each time — because building it fresh would break caching, which is the exact bug the tool reports as CACHE_INVALIDATOR. Being your own first customer is a good line in an interview.

The agent loop

agent.py — about forty lines, and worth knowing cold

In plain words

This is the version where the reviewer decides what to read. It gets two tools — search the code, and open a file — and works until it's satisfied.

Why bother? Because it can follow a thread. It reads a file, sees it mentions a handler defined somewhere else, and goes and opens that too — to check whether a tool's actual behaviour matches what its description promises. You cannot prepare that question in advance, because which file matters depends on what it just found.

Learn this shape. Every coding agent, including the one that built this project, is this loop going round:

Four things that are real bugs if you get them wrong

  1. Record the model's turn before running tools. The request to use a tool lives in that message. Send back a result whose request is missing from the history and the API rejects it.
  2. All results go back in one message. Splitting them across several quietly teaches the model to stop asking for things in parallel — so it gets slower, and nothing tells you why.
  3. Hand tool errors back, don't crash. Mark it as an error and let the model try something else.
  4. Cap the loop. Fourteen turns here. An uncapped agent loop is the standard way an AI project becomes a surprise bill.

The security bit

The model supplies file paths, so those paths are untrusted input. Every one is resolved and checked to be inside the project folder before anything is opened:

Without that, a malicious instruction hidden in a file being reviewed could turn "read a source file" into "read anything on this machine." Tests cover ../, absolute paths, and in-project files that aren't in scope.

If they ask about prompt injection

The general principle: anything the model produces is untrusted input to your code. Validate tool arguments the same way you'd validate a form submitted by a stranger on the internet — because functionally that's what it is.

Retrieval, and why it isn't used

retrieval/ — RAG, and the discipline of not needing it

In plain words

RAG means: search your documents, paste the results into the question, ask the model. That's the whole concept. If you've ever pasted a page of a manual into a chat before asking about it, you've done it manually.

The only question that matters is: does the information fit in the question? If yes, put it there and stop. You don't need a search system.

In this project, the answer is yes — the model catalog is a few hundred lines. So the analyser doesn't use retrieval at all, and says so out loud in the README.

The folder exists as a worked example, with both approaches behind the same interface: ordinary keyword search, and meaning-based search.

The demo that makes the point

Keyword search works well when the words in the question match the words in the document — which for technical docs is most of the time. Here it is failing, from a real run:

The documents contain the answer — it's the cache-minimum trap from earlier. But keyword search latched onto "went" and "after", filler words, and returned junk with a confident-looking score.

That's the honest case for meaning-based search, and it's the right way to decide: find real questions where the cheap method fails, then upgrade. Not "we used embeddings because that's what RAG means."

The mistake that ruins most RAG systems

Chopping documents into equal-sized blocks. It's the fast thing to write and it poisons everything downstream, because a fragment stripped of its context gets returned for questions it has nothing to do with:

The fix: split on headings, and keep the trail of headings attached to every piece. Now it can't be misread, and the model can say where it came from.

"What should k be?"

k is just how many search results you take. The trouble is you pick the number before you know how much the question needs — too few and the answer is missing, too many and it drowns in noise.

The real method: write down about twenty real questions where you know the right answer, try k=3, 5, 10, 20, and pick the smallest number where accuracy stops improving.

The better answer is to not have a k. Either fetch twenty and have a cheap second pass throw out the irrelevant ones, or give the model search as a tool and let it decide when it has enough.

If they ask you to design a RAG system

"First I'd check whether the information fits in the prompt — if it does, RAG is premature. If not, I'd ask whether one search answers the question or whether it needs several. One search over a fixed set of documents, classic RAG is fine and cheaper. Otherwise I'd give the model search as a tool and let it iterate. And if the data is structured — customers, orders, dates — I'd query it directly rather than embedding it."

How you test it

Where most interview answers fall apart

In plain words

You cannot unit-test a loop that picks its own steps. There's no fixed sequence to assert on.

So you don't test the model's choices. You test the machinery around them — and you test outcomes against a set of examples you've graded by hand.

Testing the agent without the internet

The loop tests use a stub — a fake stand-in that returns a scripted list of responses instead of calling the real API. They run offline, instantly, and give the same answer every time. What they check:

  • Each tool result is matched to the right request
  • All results come back in one message, not several
  • A bad file path is handed back as an error, not crashed on
  • The sandbox rejects paths outside the project
  • The loop stops at its cap instead of running forever

None of that is about whether the model is smart. It's about whether the harness is correct. That distinction is the answer.

The two fixtures

FilePurpose
sick_app.py Deliberately broken. Every defect in it is one that ships in real code.
healthy_app.py Deliberately clean. The suite asserts the tool stays quiet — because a linter that can't be satisfied gets turned off.

Why "no tests" is a High finding

The tool flags a codebase that has no test checking what the model actually returns. It also flags the sneakier case: tests that exist but fake the model every time. Those verify you built the request you meant to build. They cannot tell you the answer got worse.

The wording in the finding says why it's ranked so high: every other recommendation in this report is unverifiable without one. Switch models, lower the effort setting, shorten the prompt — you can't safely do any of it if nothing measures whether quality dropped.

If they ask "how would you know it's working?"

Twenty to fifty real inputs, graded by hand, asserting on properties rather than exact wording, run automatically. Then say the honest part: without that, every performance or cost improvement you make is a guess.

Likely questions

Short answers, in your own words

"Walk me through the architecture."

Find the API calls in the code. Turn each into a tidy record of what settings it was given. Run thirty small rule-based checks over those records. Separately, send the relevant files to Claude for the questions no rule can answer. Merge, rank by severity, print a report. The rule-based part needs no model and no network.

"Why not use a model for everything?"

Because a lookup is not a judgement call. A table answers "is this retired?" correctly every time, for free. Reserve the model for questions with no right answer written down anywhere.

"How do you decide agent vs. workflow?"

Can I write the steps down before starting? If yes, workflow — cheaper and testable. If the next step depends on what I discover, I need a loop. This project has both, on purpose.

"What happens when it's wrong?"

Two guards. Checks must prove a problem from the facts or stay silent. And every report ends with a section saying what wasn't checked — how many settings couldn't be read, which languages were only skimmed. A report that hides its blind spots reads as a clean bill of health, which is worse than no report.

"How would you scale this to a thousand repositories?"

The rule-based part already scales — it's local and fast, run it in parallel. The model part is the cost. I'd run rules on everything, then only pay for judgement on repos where the rules found something interesting. And I'd cache the fixed instructions so I'm not re-paying for them on every repo.

"What would you do next?"

Properly parse JavaScript and TypeScript — right now they're only skimmed, which is the biggest blind spot. Have the auto-fix open a pull request instead of editing files in place. And base the cost estimates on real usage data rather than inferring them from how the request looks.

"What's the weakest part?"

Say this one plainly, because it's true and it's the kind of honesty that lands well: the model-powered paths are the least verified. The loop is tested against a stub, so the machinery is sound, but a wrong setting name would only show up on a real call. It's written down as a known limitation in the pull request rather than glossed over.

If you remember five things

  1. Deterministic where the shape is known, model judgement where it isn't. That's the whole design.
  2. Workflow if you can name the steps; loop if you can't.
  3. The silent failures are the point — the cache minimum that stops working after an upgrade, with no error anywhere.
  4. You test an agent's harness, not its choices, and you measure outcomes against examples you graded yourself.
  5. Say what you didn't check. A report that hides its blind spots is worse than no report.
