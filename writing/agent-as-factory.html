Your AI agent is a factory

July 2026  ·  5 min read

The most useful way to think about agent reliability may come from the factory floor.

I spent part of my career in global R&D at Harry's, where everything we designed had to survive being manufactured at scale. For the last year I've been building AI workflows, and I keep seeing the same shape. A request comes in, a process transforms it, and an output comes out, sometimes excellent and sometimes subtly wrong. If the work matters, "it usually works" isn't a quality strategy.

Factories solved this problem a long time ago. Five of their ideas carry straight over to agents.

1. Fix the line, not the operator

Treat the model, prompt, tools, and orchestration as production equipment, and each run as the unit being produced. The account brief, the resolved ticket, the updated CRM record: that's what leaves the factory.

When a part comes off the line out of tolerance, a good manufacturing team checks the material, the instructions, the machine, and the inspection method before telling the operator to be more careful. Agent failures deserve the same treatment. A made-up number might come from a weak model, or just as easily from stale data, an ambiguous task, a failed search, or a tool returning the wrong field. "The model got it wrong" is usually as shallow a diagnosis as "the factory made a bad part."

2. Inspect how it was made

The eval systems I trust check the whole run: what the agent read, which tools it called, what came back, and what it changed.

Say an agent produces a flawless-looking due-diligence report. A grader that only reads the report approves it. The run record shows the agent never opened two required documents and pulled a number from an outdated filing. The part passed inspection with the wrong metal inside it. For low-stakes work, checking the output is enough. For a hiring decision, a financial recommendation, or anything that writes to a system of record, how the output was made is part of the product.

3. Stop the line on real defects

Toyota lets any worker stop the production line when something looks wrong, so a defect never travels downstream. Agents need the same thing: checks that block delivery and send the work back for revision before it reaches anyone. A dashboard that reports bad outputs after they've shipped is a returns report. It's useful for learning, and too late to stop anything.

Not every defect should stop the line. An awkward sentence can ship. An unsupported legal conclusion can't. Critical failures need hard limits, because in a weighted average, five strong scores can cancel out one catastrophic one.

And check the checker. If a grader scores the same output 0.9 on Monday and 0.6 on Tuesday, the gauge is broken, not the agent. Use plain code wherever you can. In Henry, the margin math runs in ordinary code, never in the model. Where you need a model to judge, test that judge against people who actually do the work.

4. Count the cost of accepted work

Most teams measure cost per run. The number that matters is cost per accepted output: everything you spent, including retries, checks, and human review, divided by the outputs that were actually good enough to use.

This flips decisions that look obvious. A small model can cost half as much per attempt, then need more retries and more reviewer time. A larger model can be cheaper overall because more of its work is accepted the first time.

The number I watch most is first-pass yield: the share of runs that pass every check the first time. An agent that eventually passes 95% of the time can still be a mess if only half its runs pass on the first try. Every retry is rework, and rework hides behind a respectable final number.

5. Put the person at the point of no return

Factories concentrate inspection where a mistake would cost the whole run. You approve the first part before the run starts, because a defect caught on that part costs an afternoon, and the same defect found after a shipment reaches a retailer costs the shipment, the freight, and the chargebacks.

Agents work the same way. Two questions decide where a person should review: how expensive is being wrong, and can you take it back? A wrong draft can be expensive and still free to fix. A wrong email can be cheap and permanently sent.

The actions you can't undo are a short, knowable list: moving money, sending a message, publishing, deleting, promising something to a customer, or writing to a record other systems trust. Before that line, an agent can retry freely. So put the person at the last moment the work can still be undone. Reviewing every step wastes attention, and reviewing after delivery is too late.

Every failure becomes a test

The best habit from manufacturing is what happens after a defect. When a check catches a failure in a live run, that run becomes a new test case, so the failure can be reproduced. The team fixes the process, not just the one bad output, and the test makes sure the failure can't quietly come back.

Redoing one weak brief is a correction. Changing the system so it happens less, and adding a test so you'd know, is how quality improves.

The factory is the product

The analogy has limits. Agents don't produce identical parts, and the same task can run differently twice. But the biggest mistake in enterprise AI is judging how smart the model is while ignoring how reliable the system around it is. The useful questions are the factory's questions. What's the specification? Where should each failure be caught? Which defects stop delivery? What happens to a failure once it's found? The model matters, but the lasting advantage comes from defining quality, measuring it honestly, and feeding what you learn back into the process.
